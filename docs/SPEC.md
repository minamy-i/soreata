## アプリ概要
仮称：それ！できて当たり前？
「できて当たり前」とされる行動・指示を、要素と必要な能力に分解し対応を提案するアプリ。
分解の矛先は人でなく困りごと。
診断でなく、困りごとの要素分解図。

## ユーザケース（バグリスト5,6より）
- 5.顔を見分けられないことの対応方法（「太郎くんの後ろに並んで」の指示に従って欲しい）
- 6.耳からの情報が簡単には頭に入らない（手順の説明と同時作業についていけない）

## 理念
できないことは、欠陥でなく、どこかの段階に壁がある。
「元々その要素に対する能力がない人もいる」という認識を社会に広めたい。
掘る行為そのものが、ほとんどの人にはできないスキル。
soreata は「掘れる人の目」を掘れない人に貸す道具。
「行動を変える」のではなく「前提条件を特定する」。
前提が見えれば、対応は「修正」ではなく「補う・代替する」になる。

## 語彙定義
- 困りごと：ユーザが入力する行動・指示。プロンプト内部では「課題」と表記。
- 要素：困りごとの中の、認識・理解・実行が求められる構成部品。分析枠として人・物（動植物を含む）・動作・空間・時間・知識の6カテゴリを使う。
- 能力：各要素を扱うために人に必要な機能。元々ない場合もある。
- 対応：各能力に対して取れる支援・代替方法
- 分解：困りごとを要素に分け、必要な能力を掘り出す行為
- ユーザ：アプリを使う人（先生・親・支援者・当事者本人など）
- 当人（対象者）：困りごとが難しい当事者。
- 当人：アプリ画面上の表示のみ（＝当人（対象者）と同一人物）。本文には素の当人を出さない。
- 当人は？：各能力について、当人（対象者）の内側の体験を示すセクション名。
- ゲスト：ログインしていない状態のユーザ
- 当人権限者：チームの管理権限を持つ人。当人（対象者）本人のことも、保護者・支援者などの別人のこともある。
- 当人権限：当人権限者が持つ管理権限（role='owner'）。他メンバーへ移す操作を「移譲」と呼ぶ。
- 協力者：当人権限者からチームへ招待された人。協力するチームの記録を権限の範囲内で閲覧・操作できる。

## 機能仕様

### UIの流れ
1. ユーザが困りごと（行動・指示）を入力する
2. 「分解する」ボタンを押すとAPIを呼び出す
3. アコーディオンで能力ごとに詳しい説明・当人は？・対応を表示する

### 入力
ユーザが行動・指示を自由入力する。
フォーマット指定なし。

### 分解・提案（全出し・アコーディオン表示）
タップで展開・収納できる。
各能力のアコーディオン本文は、説明・当人は？・対応の順で表示する。各セクション間は視覚的に区切る（実装時に決定）。

### コピーボタン
分解・対応の一覧カードにコピーボタンを配置する。
押すと全能力のタイトルと本文をテキスト形式でクリップボードにコピーする。
2秒間「コピーしました」と表示後、元に戻る。

### グローバルナビゲーション

ページ上部に固定表示（スクロールしても残る）。
現在表示中のページに対応するリンクを白背景・濃色テキストで反転表示する（アクティブ状態）。
スマホ（600px未満）ではリンクテキストを短縮表示する（困りごとのAI分解→AI分解、ダッシュボード→記録）。

| 項目 | 遷移先 | 表示条件 |
|---|---|---|
| AI分解 | `/` | 全員 |
| ダッシュボード | `/account` | ログイン済みのみ |
| Googleでログイン | `/login` | 未ログインのみ |

### 困りごとのAI分解画面のログイン状態による出し分け

**分解・クリアボタン周辺**
- ログイン済み＋チーム所属あり：「分解後に保存できます」
- ログイン済み＋チーム0件：「保存にはチームが必要です」＋「チームを作成する」リンク（`/account`へ遷移）
- 未ログイン：「結果を保存するにはチームが必要です」＋ログインリンク
  - 常時表示（クリック展開ではない）：「結果を保存するにはチームが必要です。ログイン後、チームを作成するか、既存チームからの招待をお待ちください。」

**結果エリア（コピーボタン横）**
- ログイン済み＋チーム所属あり：「保存する」ボタン（保存フローは「保存フロー」参照）
- ログイン済み＋チーム0件：ボタン非活性
- 未ログイン：何も出さない（コピーボタンのみ）

ログインボタン：未ログイン時のみ表示。

### ログインページ（/login）

ダッシュボードへ直接アクセスする人の入口。

- 「Googleでログイン」ボタンのみのシンプルな画面
- ログイン後は常に `/account` へ遷移する。元のURLへは戻らない。
- 未ログインでどのURLにアクセスしても、ログイン後はアカウントダッシュボードへ誘導する。

### アクセス制御（全ページ共通）
`/home/[team_id]`配下の全ページ（記録詳細・チーム設定を含む）に適用する。
- 未ログイン：どのURLにアクセスしてもログイン画面へ誘導し、ログイン後は`/account`へ（元のURLには戻らない）
- ログイン済みだが対象チームの権限が無い、または自分の行に空セルが残っている：`/account`へリダイレクト

### 認証・登録フロー
- ログイン：Googleログイン（1つの入口）`/account`へ遷移
- accounts行は初回ログイン時に認証コールバック（`app/auth/callback/route.ts`）で作成する
- メアドは表示のみ（Googleアカウントで管理・アプリ側での変更なし）
- ログイン直後は「空アカウント」（どのチームにも所属しない状態）。チーム・当人権限者は自動生成しない
- チームは「チームを作成する」ボタンによる明示的な操作でのみ作成する
- チーム0件のアカウントも特別扱いしない。ナビバー・AI分解画面など通常のUIをそのまま表示する

### チームページ（/home/[team_id]）
当人権限者・協力者が同一URLでアクセスする。
ログイン中の権限（role）で表示・操作を切り替える。

| 機能 | 当人権限者 | 協力者 |
|---|---|---|
| AI分解の記録 | 作成・閲覧可 | 作成・閲覧可 |
| └ 能力確認日 | 入力・変更可 | 入力のみ |
| メンバー一覧（ニックネーム・relationship・role） | 閲覧可 | 閲覧可 |
| チーム設定（チーム名・削除・外部連携・当人権限移譲・協力者招待） | 編集可 | 通常は表示なし（Webhook連携の管理を委譲された場合のみ、リンク自体が表示される） |

- AI分解記録：1件 = 日付 ＋ 困りごと（task_text）
- 記録ゼロ時：「分解して保存してみましょう」の案内を表示
- チーム名・自分のニックネームを常時表示する（編集は`/account`のチーム一覧表で行う。「チーム一覧の表」参照）

### アカウントダッシュボード（/account）
状況に応じて次を表示する。促し文は付けず、ボタンを置くだけ。
- メアド（表示のみ）
- チーム一覧の表（マイチーム・協力チーム。「チーム一覧の表」参照）
- 来ている招待一覧 ＋「参加」ボタン（受諾するとteam_membersにcollaborator行が作られる）
- 「チームを作成する」ボタン
- ログアウト
- 退会ボタン（team_membersに自分の行が0件の場合のみ表示）

ニックネームはアカウント共通では持たない。チームごとにteam_membersが持つ（下記チーム一覧の表参照）。

### チーム一覧の表（/account）
所属する全チーム（当人権限者・協力者どちらの立場も含む）を1つの表で表示する。列はチーム名・自分のニックネーム・relationship。
- 各セルは表の上で直接クリックして編集する。別ページ・別フォームは開かない
- 行に空セルがあると、そのチームへは入れない（`/home/[team_id]`へのリンクが無効）。全セルが埋まって初めて入れる
- 全セルが埋まっている行はいつでも自由にセルを編集できる（入場をブロックしない）。空にした場合は次回また同じルールでブロックされる
- 何もない行（協力者0人・保留中の招待0件・AI分解記録0件）には軽い「削除」リンクを表示し、確認ダイアログなしで即削除できる（誤って作成した場合の取り消し用。「チーム設定」の削除機能とは別）

### チーム作成フロー
「チームを作成する」ボタンを押すと、チーム一覧の表に新しい空行が増える。
1. 呼び名・自分のニックネーム・relationshipの3セルを、その場で入力する（別ページ・別フォームは開かない）
2. 3つとも埋めて確定すると、teams（作成者をcreated_byに。nameは呼び名から自動で「チーム」を前置。例：「太郎」→「チーム太郎」）＋team_members（role='owner'）を同時作成する
3. `/home/[team_id]`へのリンクが有効になる

### チーム設定（/home/[team_id]/settings）
当人権限者専用の管理ページ。ニックネーム編集はここでは行わない（「チーム一覧の表」参照）。
同じページ内で、権限によって表示範囲を分ける。
- 当人権限者：以下すべてが見える
  - チーム名（teams.name）の編集
  - チームの削除：協力者0人・保留中の招待0件・AI分解記録0件なら即削除（`/account`のチーム一覧表からも可）。それ以外は確認ダイアログを伴う通常の削除フロー（確認ダイアログの文言・削除範囲の詳細は検討中）
  - 外部ツールへの投稿設定（Slack/Discord Webhook URL・委譲する協力者の指定）
  - 当人権限（owner）移譲の指名（相手は承諾制。「当人権限（owner）移譲」参照）
  - 協力者を招待する（招待フロー参照）
  - 招待中一覧（送信済み・未受諾の招待のメアド一覧）＋取り消しボタン
- Webhook連携の管理を委譲された協力者：外部ツールへの投稿設定（Slack/Discord Webhook URL）のみが見える。他のセクションは表示されない

### AI分解記録詳細（/home/[team_id]/record/[id]）
- 保存日・困りごと（編集不可）
- 能力一覧：アコーディオン形式
  - ヘッダー：◻︎ タイトル ＋ 確認日（◻︎は印刷用・装飾のみ・操作なし）
  - 本文（展開時）：説明・当人は？・対応（困りごとのAI分解画面と同じ表示）
  - 確認前：確認日 ——
  - 確認後：確認日 YYYY-MM-DD
  - 確認日の操作：入力（全員可）・変更・削除（当人権限者のみ）
- 外部ツールへの投稿ボタン：チームにWebhook URLが設定されている場合のみ表示。押すとこの記録の全能力のタイトル・本文をSlack/Discordへ送信する（コピー機能と同じテキスト）
  - 投稿済みなら、ボタンの近くに「前回投稿：YYYY-MM-DD HH:MM」を表示する（decompositions.posted_at）。再投稿はブロックしない。確認ダイアログや警告も出さない
- 削除ボタン（確認ダイアログあり）

### 保存フロー
保存先候補は、自分の行（nickname・relationship）が全セル埋まっているチームのみ（空セルが残っているチームは候補に含めない）。

1. AI分解後「保存する」ボタンを押す（ログイン済みのみ表示）
   - 未ログイン：ボタン非表示
   - ログイン＋保存先候補0件：ボタン非活性・/account への誘導（チーム自体が0件の場合も、全チームが空セル持ちの場合も同じ扱い）
   - ログイン＋保存先候補1件：ボタン押下で確認（「チーム太郎に保存しますか？」等、チーム名を明示）を経て保存。1件でも自動保存はしない（別の対象者の分析結果を勘違いして保存する事故を防ぐため）
   - ログイン＋保存先候補複数：ボタン押下でチーム選択UIを表示
2. abilities JSON に全フィールド（title・description・person・solution・confirmed_at）を保存
3. 保存完了 → 記録詳細（/home/[team_id]/record/[id]）へ遷移

### 招待フロー（協力者登録）
招待は team_members に協力者を入れる唯一の手段。**招待できるのは、既に登録済みのアカウントのメールアドレスのみ**（招待リンクという仕組みは持たない）。
1. 当人権限者がチーム設定で協力者のメアドを入力する
2. サーバー側（サービスロールキー使用。RLSの制限を受けない）で、そのメアドが登録済みアカウントと一致するか即座に確認する
   - 一致しない場合：「このメールアドレスは登録されていません。相手にログインしてもらってから、もう一度招待してください」と表示し、招待は作らない
   - 一致する場合：invitations（team_id・invited_email）に保存する
3. 次回ログイン時に /account に招待が表示され、「参加」ボタンで受諾する
4. 受諾は必ず /account での明示操作。新規登録しただけでは自動的にチームへ参加しない
5. 受諾でteam_membersにcollaborator行が作られる（nickname・relationshipはNULLのまま。チーム名は既にあるので空セルは2つだけ。`/account`のチーム一覧表で入力するまで、そのチームには入れない）。invitationsの該当行は削除される
- 未登録の相手には、当人権限者が個別に連絡し（LINE等）、先にsoreataへログインしてもらってから招待する
- 通知手段は当面この方式のみ。外部メールサービスによる自動送信は行わない

## AIの役割・プロンプト設計方針
- few-shot の例は prompt.js の EXAMPLES 定数に直接埋め込んでいる

### 分解の原則（プロンプト設計の核）
→ prompt.js 参照

### 分析フレームワーク（AIの内部分析枠・ユーザには見せない）
以下の6カテゴリを網羅的に掘る枠として使う。
- 人：関わる人物の特定・理解
- 物（動植物を含む）：関わる物・生き物の特定・理解
- 動作：実行すべき行動の理解と制御
- 空間：位置・方向・境界線などの空間認識
- 時間：時間感覚・タイミング・手順の時系列
- 知識：前提となるルール・慣習・概念の理解

### 品質基準（生命線テスト）
以下2課題は few-shot 例としてプロンプトに含まれているため正しく出力される。
- 「太郎くんのうしろに並んで」→ 顔を見分ける能力
- 「大玉送りで相手チームの邪魔に行かない」→ 言葉にされていない暗黙のルール

合格ラインは、例にない他の困りごとを入力した場合も、同レベルの深さで隠れた能力を掘り出せること。
このレベルが汎化できなければ、soreata はただの手順分解アプリになる。合格基準は下げない。
現採用モデル（Gemini 3.1 Flash Lite）は宿題提出のため。本番運用時はモデルを改めて選定する。

## 検討中の仕様
以下はスキーマ・大枠は確定しているが、UI・詳細フローは未確定の機能。

### 当人権限（owner）移譲
スキーマは確定（team_membersのrevoked_at＋新owner行による履歴型の付け替え。owner一意の部分ユニークインデックスで保証）。
承諾制とする。チーム設定ページで移譲先の協力者を指名し、相手が/accountで明示的に承諾するまで切り替わらない（招待フローと同じ「保留→受諾」の型を踏襲）。
保留状態は専用テーブル`ownership_transfers`（id・team_id・to_account_id・created_at）で持つ。invitationsは流用しない（招待は未確定のemail宛、移譲は既に確定しているaccount_id宛で性質が違うため）。
承諾時：team_members の旧owner行をrevoked_at、to_account_idの協力者行もrevoked_atにし、to_account_idの新owner行を作成。ownership_transfersの該当行は削除する。

### 外部ツールへの投稿（Slack/Discord連携）
AI分解記録のコピー機能と同じテキストを、Slack・DiscordのWebhook URLへワンボタンで投稿できる。一方通行の送信のみ（読み込み・bot連携は行わない）。
- 送信先URL・対応先（Slack/Discord）はteams（webhook_url・webhook_platform）に持つ。任意項目
- 対応先はSlack・Discordの2つに限定する
- 設定変更は当人権限者、または`team_members.can_manage_webhook`（boolean）がtrueの協力者のみ。複数人に許可してよい

### 未決事項
- 外部メールサービス（招待メール自動送信。今は導入しない方針・将来検討）
- チーム削除（確認ダイアログを伴う通常フロー）の文言・削除範囲の詳細

## 技術方針
- フレームワーク：Next.js（App Router・TypeScript）
- Vercel にデプロイ
- DB：Supabase（PostgreSQL）。テーブル構成は `docs/data_structure.md` 参照。
- 認証：Supabase Auth（Google OAuth）
- `prompt.ts`：EXAMPLESとbuildPromptを一元管理する共有モジュール。API routeから参照。
- `app/api/decompose/route.ts`：Next.js API route。プロンプト組み立てと Gemini API 呼び出しを担う。能力一覧・当人は？を一括で返す。
- `demo.html`：プロトタイプ用のデモ。仕様対象外。
- `data/samples.json`：実出力サンプルデータ。スキーマ：[{id, task, createdAt, abilities: [{title, description, person, solution}]}]。
- APIキーは環境変数（`GEMINI_API_KEY`）で管理。コードには書かない。
- モデル：Gemini 3.1 Flash Lite（`gemini-3.1-flash-lite`）
