## アプリ概要
仮称：それ！できて当たり前？
「できて当たり前」とされる行動・指示を、要素と必要な能力に分解し対応を提案するアプリ。
分解の矛先は人でなく困りごと。
診断でなく、困りごとの要素分解図。

## ユーザケース（バグリスト5,6より）
- 5.顔を見分けられないことの対応方法（「太郎くんの後ろに並んで」の指示に従って欲しい）
- 6.耳からの情報が簡単には頭に入らない（手順の説明と同時作業についていけない）

## 理念
できないことは、欠陥でなく、どこかの段階に壁がある。
「元々その要素に対する能力がない人もいる」という認識を社会に広めたい。
掘る行為そのものが、ほとんどの人にはできないスキル。
soreata は「掘れる人の目」を掘れない人に貸す道具。
「行動を変える」のではなく「前提条件を特定する」。
前提が見えれば、対応は「修正」ではなく「補う・代替する」になる。

## 語彙定義
- 困りごと：ユーザが入力する行動・指示。プロンプト内部では「課題」と表記。
- 要素：困りごとの中の、認識・理解・実行が求められる構成部品。分析枠として人・物（動植物を含む）・動作・空間・時間・知識の6カテゴリを使う。
- 能力：各要素を扱うために人に必要な機能。元々ない場合もある。
- 対応：各能力に対して取れる支援・代替方法
- 分解：困りごとを要素に分け、必要な能力を掘り出す行為
- ユーザ：アプリを使う人（先生・親・支援者・当事者本人など）
- 当人（対象者）：困りごとが難しい当事者。
- 当人：アプリ画面上の表示のみ（＝当人（対象者）と同一人物）。本文には素の当人を出さない。
- 当人は？：各能力について、当人（対象者）の内側の体験を示すセクション名。
- ゲスト：ログインしていない状態のユーザ
- 当人権限者：チームの管理権限を持つ人。当人（対象者）本人のことも、保護者・支援者などの別人のこともある。
- 当人権限：当人権限者が持つ管理権限（role='owner'）。他メンバーへ移す操作を「移譲」と呼ぶ。
- 協力者：当人権限者からチームへ招待された人。協力するチームの記録を権限の範囲内で閲覧・操作できる。

## 機能仕様

### UIの流れ
1. ユーザが困りごと（行動・指示）を入力する
2. 「分解する」ボタンを押すとAPIを呼び出す
3. アコーディオンで能力ごとに詳しい説明・当人は？・対応を表示する

### 入力
ユーザが行動・指示を自由入力する。
フォーマット指定なし。

### 分解・提案（全出し・アコーディオン表示）
タップで展開・収納できる。
各能力のアコーディオン本文は、説明・当人は？・対応の順で表示する。各セクション間は視覚的に区切る（実装時に決定）。

### コピーボタン
分解・対応の一覧カードにコピーボタンを配置する。
押すと全能力のタイトルと本文をテキスト形式でクリップボードにコピーする。
2秒間「コピーしました」と表示後、元に戻る。

### グローバルナビゲーション

ページ上部に固定表示（スクロールしても残る）。
現在表示中のページに対応するリンクを白背景・濃色テキストで反転表示する（アクティブ状態）。
スマホ（600px未満）ではリンクテキストを短縮表示する（困りごとのAI分解→AI分解、ダッシュボード→記録）。

| 項目 | 遷移先 | 表示条件 |
|---|---|---|
| AI分解 | `/` | 全員 |
| ダッシュボード | `/account` | ログイン済みのみ |
| Googleでログイン | `/login` | 未ログインのみ |

### 困りごとのAI分解画面のログイン状態による出し分け

**分解・クリアボタン周辺**
- ログイン済み＋チーム所属あり：「分解後に保存できます」
- ログイン済み＋チーム0件：「保存にはチームが必要です」＋チーム作成への誘導（具体的な文言は検討中）
- 未ログイン：「結果を保存するには分解前にログインしてください」＋ログインリンク

**結果エリア（コピーボタン横）**
- ログイン済み＋チーム所属あり：「保存する」ボタン（保存フローは「保存フロー」参照）
- ログイン済み＋チーム0件：ボタン非活性
- 未ログイン：何も出さない（コピーボタンのみ）

ログインボタン：未ログイン時のみ表示。

### ログインページ（/login）

ダッシュボードへ直接アクセスする人の入口。

- 「Googleでログイン」ボタンのみのシンプルな画面
- ログイン後は常に `/account` へ遷移する。元のURLへは戻らない。
- 未ログインでどのURLにアクセスしても、ログイン後はアカウントダッシュボードへ誘導する。

### 認証・登録フロー
- ログイン：Googleログイン（1つの入口）`/account`へ遷移
- メアドは表示のみ（Googleアカウントで管理・アプリ側での変更なし）
- ログイン直後は「空アカウント」（どのチームにも所属しない状態）。チーム・当人権限者は自動生成しない
- チームは「チームを作成する」ボタンによる明示的な操作でのみ作成する
- チーム0件のアカウントも特別扱いしない。ナビバー・AI分解画面など通常のUIをそのまま表示する

### チームダッシュボード（/home/[team_id]）
当人権限者・協力者が同一URLでアクセスする。
ログイン中の権限（role）で表示・操作を切り替える。

| 機能 | 当人権限者 | 協力者 |
|---|---|---|
| AI分解の記録 | 作成・閲覧可 | 作成・閲覧可 |
| └ 能力確認日 | 入力・変更可 | 入力のみ |
| 観察記録（検討中） | 投稿・自分のもの編集可 | 投稿・自分のもの編集可 |
| 会議室（検討中） | 投稿・コメント・まとめ依頼・まとめ記述・承諾可 | 投稿・コメント・まとめ記述可 |
| 当人権限者情報設定 | 編集可 | 表示なし |
| 協力者一覧（検討中） | 管理・招待可 | 閲覧可 |
| └ 協力者招待 | 可 | 不可 |

- AI分解記録：1件 = 日付 ＋ 困りごと（task_text）
- 記録ゼロ時：「分解して保存してみましょう」の案内を表示

### アカウントダッシュボード（/account）
状況に応じて次を表示する。促し文は付けず、ボタンを置くだけ。
- メアド（表示のみ）
- ニックネーム（編集可）
- マイチーム（当人権限者として）→ チームダッシュボードへ
- 協力チーム一覧（協力者として）→ チームダッシュボードへ
- 来ている招待一覧 ＋「参加」ボタン（受諾するとteam_membersにcollaborator行が作られる）
- 「チームを作成する」ボタン
- ログアウト
- 退会ボタン（team_membersに自分の行が0件の場合のみ表示）

### 当人権限者情報設定（/home/[team_id]/settings）
- team_members.nickname 編集（自分の当人権限者としての呼び名）
- 当人権限者のみ表示
- 詳細内容は検討中（「検討中の仕様」参照）

### AI分解記録詳細（/home/[id]/record/[id]）
- 保存日・困りごと（編集不可）
- 能力一覧：アコーディオン形式
  - ヘッダー：◻︎ タイトル ＋ 確認日（◻︎は印刷用・装飾のみ・操作なし）
  - 本文（展開時）：説明・当人は？・対応（困りごとのAI分解画面と同じ表示）
  - 確認前：確認日 ——
  - 確認後：確認日 YYYY-MM-DD
  - 確認日の操作：入力（全員可）・変更・削除（当人権限者のみ）
- 削除ボタン（確認ダイアログあり）

### 保存フロー
1. AI分解後「保存する」ボタンを押す（ログイン済みのみ表示）
   - 未ログイン：ボタン非表示
   - ログイン＋チーム0件：ボタン非活性・/account への誘導
   - ログイン＋チーム1件：ボタン押下で自動的にそのチームへ保存
   - ログイン＋チーム複数：ボタン押下でチーム選択UIを表示
2. abilities JSON に全フィールド（title・description・person・solution・confirmed_at）を保存
3. 保存完了 → 記録詳細（/home/[id]/record/[id]）へ遷移

### 招待フロー（協力者登録）
招待は team_members に協力者を入れる唯一の手段。
1. 当人権限者がアプリ内で協力者のメアドを入力し、招待を作成する
2. サーバーがトークンを生成し、invitations（team_id・invited_email・token）に保存する
3. 相手が登録済みの場合：次回ログイン時に /account に招待が表示され、「参加」ボタンで受諾する
4. 相手が未登録の場合：当人権限者が招待リンク（遷移先 /login）を自分でコピーして手渡す（LINE・メール等）。相手はリンクからログインすると登録済みと同じ流れ（/account に招待表示 →「参加」）に合流する
5. 受諾は必ず /account での明示操作。リンクを開いた・新規登録しただけでは自動的にチームへ参加しない
6. 受諾でteam_membersにcollaborator行が作られる（ニックネーム・relationshipはこの時または参加後に登録）
- 通知手段は当面リンク手渡しのみ。外部メールサービスによる自動送信は行わない

## AIの役割・プロンプト設計方針
- few-shot の例は prompt.js の EXAMPLES 定数に直接埋め込んでいる

### 分解の原則（プロンプト設計の核）
→ prompt.js 参照

### 分析フレームワーク（AIの内部分析枠・ユーザには見せない）
以下の6カテゴリを網羅的に掘る枠として使う。
- 人：関わる人物の特定・理解
- 物（動植物を含む）：関わる物・生き物の特定・理解
- 動作：実行すべき行動の理解と制御
- 空間：位置・方向・境界線などの空間認識
- 時間：時間感覚・タイミング・手順の時系列
- 知識：前提となるルール・慣習・概念の理解

### 品質基準（生命線テスト）
以下2課題は few-shot 例としてプロンプトに含まれているため正しく出力される。
- 「太郎くんのうしろに並んで」→ 顔を見分ける能力
- 「大玉送りで相手チームの邪魔に行かない」→ 言葉にされていない暗黙のルール

合格ラインは、例にない他の困りごとを入力した場合も、同レベルの深さで隠れた能力を掘り出せること。
このレベルが汎化できなければ、soreata はただの手順分解アプリになる。合格基準は下げない。
現採用モデル（Gemini 3.1 Flash Lite）は宿題提出のため。本番運用時はモデルを改めて選定する。

## 検討中の仕様
以下はスキーマ・大枠は確定しているが、UI・詳細フローは未確定の機能。

### 観察記録（/home/[team_id]/memo・検討中）
追記型タイムライン。
- 全員（当人権限者・協力者）が投稿可
- 作成者のみ編集可
- タイトル必須

### 会議室（/home/[team_id]/meeting・検討中）
提案・相談・連絡の場。観察記録に書く前の事前相談・合意形成に使う。
- 全員（当人権限者・協力者）が投稿・コメントできる
- 当人権限者が「まとめ依頼」ボタンを押すと投稿・コメントがロックされる
- 誰かがまとめを書く（summary_text）
- 当人権限者が「観察記録へ書き込み」ボタンを押したら完了（自動書き込み）
- 却下した場合はロック解除・summary_textは残す・議論に戻る

### 当人権限（owner）移譲
スキーマは確定（team_membersのrevoked_at＋新owner行による履歴型の付け替え。owner一意の部分ユニークインデックスで保証）。
未確定：即時切替か相手の承諾制か、実行できる場所（メンバー一覧UIの要否）。

### チーム作成の詳細
未確定：本人／代理（親・先生など）の選び方、チーム名の入力方法、このチームでの自分のnickname・relationshipの入力。

### 未決事項
- 会議室のURL（/home/[team_id]/meeting は仮）
- 外部メールサービス（招待メール自動送信。今は導入しない方針・将来検討）
- 招待リンクの強度（有効期限・1回使い切り・メアド一致の強制範囲）
- 当人権限者情報設定の内容（管理者情報など）
- チームダッシュボードのタブ構成・名前

## 技術方針
- フレームワーク：Next.js（App Router・TypeScript）
- Vercel にデプロイ
- DB：Supabase（PostgreSQL）。テーブル構成は `docs/data_structure.md` 参照。
- 認証：Supabase Auth（Google OAuth）
- `prompt.ts`：EXAMPLESとbuildPromptを一元管理する共有モジュール。API routeから参照。
- `app/api/decompose/route.ts`：Next.js API route。プロンプト組み立てと Gemini API 呼び出しを担う。能力一覧・当人は？を一括で返す。
- `demo.html`：プロトタイプ用のデモ。仕様対象外。
- `data/samples.json`：実出力サンプルデータ。スキーマ：[{id, task, createdAt, abilities: [{title, description, person, solution}]}]。
- APIキーは環境変数（`GEMINI_API_KEY`）で管理。コードには書かない。
- モデル：Gemini 3.1 Flash Lite（`gemini-3.1-flash-lite`）
