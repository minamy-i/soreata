## アプリ概要
仮称：それ！できて当たり前？
「できて当たり前」とされる行動・指示を、要素と必要な能力に分解し対応を提案するアプリ。
分解の矛先は人でなく困りごと。
診断でなく、困りごとの要素分解図。

## ユーザケース（バグリスト5,6より）
- 5.顔を見分けられないことの対応方法（「太郎くんの後ろに並んで」の指示に従って欲しい）
- 6.耳からの情報が簡単には頭に入らない（手順の説明と同時作業についていけない）

## 理念
できないことは、欠陥でなく、どこかの段階に壁がある。
「元々その要素に対する能力がない人もいる」という認識を社会に広めたい。
掘る行為そのものが、ほとんどの人にはできないスキル。
soreata は「掘れる人の目」を掘れない人に貸す道具。
「行動を変える」のではなく「前提条件を特定する」。
前提が見えれば、対応は「修正」ではなく「補う・代替する」になる。

## 語彙定義
- 困りごと：ユーザが入力する行動・指示。プロンプト内部では「課題」と表記。
- 要素：困りごとの中の、認識・理解・実行が求められる構成部品。分析枠として人・物（動植物を含む）・動作・空間・時間・知識の6カテゴリを使う。
- 能力：各要素を扱うために人に必要な機能。元々ない場合もある。
- 対応：各能力に対して取れる支援・代替方法
- 分解：困りごとを要素に分け、必要な能力を掘り出す行為
- ユーザ：アプリを使う人（先生・親・支援者・当事者本人など）
- 対象者：困りごとが難しい当事者。支援者が使う場合は直接使用者ではない。
- 当人：アプリ上での対象者の呼び方。対象者と同じ人を指す。
- 当人は？：各能力について、対象者の内側の体験を示すセクション名。
- ゲスト：ログインしていない状態のユーザ
- 当人アカウント：Googleログインで登録したアカウント。v1は当人本人が使うことを想定。

## 機能仕様

### UIの流れ
1. ユーザが困りごと（行動・指示）を入力する
2. 「分解する」ボタンを押すとAPIを呼び出す
3. アコーディオンで能力ごとに詳しい説明・当人は？・対応を表示する

### 入力
ユーザが行動・指示を自由入力する。
フォーマット指定なし。

### 分解・提案（全出し・アコーディオン表示）
タップで展開・収納できる。
各能力のアコーディオン本文は、説明・当人は？・対応の順で表示する。各セクション間は視覚的に区切る（実装時に決定）。

### コピーボタン
分解・対応の一覧カードにコピーボタンを配置する。
押すと全能力のタイトルと本文をテキスト形式でクリップボードにコピーする。
2秒間「コピーしました」と表示後、元に戻る。

### グローバルナビゲーション

ページ上部に固定表示（スクロールしても残る）。
現在表示中のページに対応するリンクを白背景・濃色テキストで反転表示する（アクティブ状態）。
スマホ（600px未満）ではリンクテキストを短縮表示する（困りごとのAI分解→AI分解、ダッシュボード→記録、アカウント設定→設定）。

- 未ログイン：「Googleでログイン」ボタン → `/login` へ遷移
- ログイン済み：「困りごとのAI分解」「ダッシュボード」「アカウント設定」リンクを表示
- v2では当人と協力者でダッシュボードのURLが異なるため、アカウント種別で出し分ける

### 困りごとのAI分解画面のログイン状態による出し分け

**分解・クリアボタン周辺**
- ログイン済み：「分解後に保存できます」
- 未ログイン：「結果を保存するには分解前にログインしてください」＋ログインリンク

**結果エリア（コピーボタン横）**
- ログイン済み：「保存する」ボタン
- 未ログイン：何も出さない（コピーボタンのみ）

ログインボタン：未ログイン時のみ表示。

### ログインページ（/login）

ダッシュボードへ直接アクセスする人の入口。

- 「Googleでログイン」ボタンのみのシンプルな画面
- ログイン後は `next` パラメータのURLへ戻る（`next` がなければダッシュボードへ）
- 例：未ログインで `/home/[id]` にアクセス → `/login?next=/home/[id]` へリダイレクト → ログイン後 → `/home/[id]` へ

### 認証・登録フロー
- ログイン：Googleログイン（1つの入口）
- 初回ログイン → アカウント設定画面へ（ニックネーム未設定の案内付き）→ 当人ダッシュボード
- 2回目以降 → 当人ダッシュボードへ

### 当人ダッシュボード（/home/[id]）
- AI分解記録一覧：1件 = 日付 ＋ 困りごと（task_text）
- 記録ゼロ時：「分解して保存してみましょう」の案内を表示
- アカウント設定へのリンク（/account/settings）
- 当人情報設定へのリンク（/home/[id]/settings）・当人のみ表示

### アカウント設定（/account/settings）
- accounts.nickname 編集
- メアド表示のみ
- ログアウト
- 退会（v1.1）
- 当人・協力者 共通で使う画面

### 当人情報設定（/home/[id]/settings）
- persons.nickname 編集
- 協力者招待（v2）
- 当人のみ表示

### AI分解記録詳細（/home/[id]/record/[id]）
- 保存日・困りごと（編集不可）
- 能力一覧：アコーディオン形式
  - ヘッダー：◻︎ タイトル ＋ 確認日（◻︎は印刷用・装飾のみ・操作なし）
  - 本文（展開時）：説明・当人は？・対応（困りごとのAI分解画面と同じ表示）
  - 確認前：確認日 ——
  - 確認後：確認日 YYYY-MM-DD
  - 確認日の操作：入力・変更・削除（未確認に戻す）
- 削除ボタン（確認ダイアログあり）

### 保存フロー
1. AI分解後「保存する」ボタンを押す（ログイン済みのみ表示）
2. abilities JSON に全フィールド（title・description・person・solution・confirmed_at）を保存
3. 保存完了 → 記録詳細（/home/[id]/record/[id]）へ遷移

### 画面構成・URL構成
`docs/screen_tree.md` 参照

## 回避事項
- 責める表示
- 人への推測（「あなたはここが弱い」型）
- 行動変容・行動評価の発想（「望ましい行動を強化する」「行動を直す」型）

## AIの役割・プロンプト設計方針
- few-shot の例は prompt.js の EXAMPLES 定数に直接埋め込んでいる

### 分解の原則（プロンプト設計の核）
→ prompt.js 参照

### 分析フレームワーク（AIの内部分析枠・ユーザには見せない）
以下の6カテゴリを網羅的に掘る枠として使う。
- 人：関わる人物の特定・理解
- 物（動植物を含む）：関わる物・生き物の特定・理解
- 動作：実行すべき行動の理解と制御
- 空間：位置・方向・境界線などの空間認識
- 時間：時間感覚・タイミング・手順の時系列
- 知識：前提となるルール・慣習・概念の理解

### 品質基準（生命線テスト）
以下2課題は few-shot 例としてプロンプトに含まれているため正しく出力される。
- 「太郎くんのうしろに並んで」→ 顔を見分ける能力
- 「大玉送りで相手チームの邪魔に行かない」→ 言葉にされていない暗黙のルール

合格ラインは、例にない他の困りごとを入力した場合も、同レベルの深さで隠れた能力を掘り出せること。
このレベルが汎化できなければ、soreata はただの手順分解アプリになる。合格基準は下げない。
現採用モデル（Gemini 3.1 Flash Lite）は宿題提出のため。本番運用時はモデルを改めて選定する。

## v2 以降の仕様

### ユーザー種別（v2）
ユーザーは2種類。ログインの入り口は1つ（Googleでログイン）で共通。
システムがDB判定で振り分ける。

| | 当人アカウント | 協力者アカウント |
|---|---|---|
| 誰が作る | 初回ログイン時（招待なし） | 当人からの招待リンク経由（初回のみ） |
| ログイン後 | 当人ダッシュボードへ | 協力者ダッシュボードへ |
| 見られるデータ | 自分の記録のみ | 担当当人の記録（権限の範囲内） |

### 認証・登録フロー（v2・協力者対応）
- 初回・招待リンクなし → 当人新規登録（ニックネーム入力）→ 当人ダッシュボード
- 初回・招待リンク経由 → 協力者新規登録（ニックネーム入力）→ 協力者ダッシュボード
- 2回目以降 → DBのアカウント種別で自動振り分け
- メアドは表示のみ（Googleアカウントで管理・アプリ側での変更なし）
- 当人がGoogleアカウントを失った場合：管理者が手動で別アカウントに移行（owner履歴テーブルで記録）

### 招待フロー（協力者登録・v2）
1. 当人がアプリ内で協力者のメアドを入力
2. サーバーがトークンを生成し、招待テーブルに保存
3. トークン入りのURLをメールで協力者に送信（外部メールサービスが必要）
4. 協力者がリンクをクリック → Googleログイン
5. サーバーがトークンを確認 → 協力者テーブルに紐付けを保存
6. 協力者がニックネームを登録 → 協力者ダッシュボードへ

### アクセス権（当人ダッシュボード・v2）
当人ダッシュボードは当人・協力者が同一URL（/home/[id]）でアクセスする。
ログイン中のアカウント種別で表示を切り替える。

| 機能 | 当人 | 協力者 |
|---|---|---|
| アカウント設定 | 編集可 | 閲覧不可 |
| 協力者一覧 | 管理可 | 閲覧可 |
| AI分解の記録 | 作成・閲覧可（編集不可） | 作成・閲覧可（編集不可） |
| └ 能力確認日 | 新規入力・変更可 | 新規入力可・変更不可 |
| 観察記録 | 作成・自分のもの編集可・閲覧可 | 作成・自分のもの編集可・閲覧可 |
| 会議室 | 投稿・コメント・まとめ依頼・承諾可 | 投稿・コメント・まとめ記述可 |

### 会議室（v2）
提案・相談・連絡の場。観察記録に書く前の事前相談・合意形成に使う。

- 全員（当人・協力者）が投稿・コメントできる
- 当人が「まとめ依頼」ボタンを押すと投稿・コメントがロックされる
- 誰かがまとめを書く（summary_text）
- 当人が「観察記録へ書き込み」ボタンを押したら完了（自動書き込み）
- 却下した場合はロック解除・summary_textは残す・議論に戻る

### 画面構成（v2以降）
画面構成図：`docs/screen_tree.md` 参照

**協力者ダッシュボード（URL未定）**
- 担当当人の一覧
- アカウント設定（ニックネーム編集・メアド表示のみ）
- 当人を選択 → 当人ダッシュボード（/home/[id]）へ

**観察記録（/home/[id]/memo）**
- 追記型タイムライン
- 全員（当人・協力者）が投稿可
- 作成者のみ編集可
- タイトル必須

**会議室（/home/[id]/meeting・仮）**
- 提案・相談・連絡の投稿・コメント（全員）
- 当人がまとめ依頼→誰かがまとめ記述→当人が承諾→観察記録へ自動書き込み

### URL構成（v2以降）
- `/home/[id]/memo`：観察記録タイムライン
- `/home/[id]/meeting`：会議室（仮）
- `/home/[id]/collaborators`：協力者一覧
- 協力者ダッシュボード：URL未定

### 未決（v2）
- 協力者ダッシュボードのURL
- 会議室のURL（/home/[id]/meeting は仮）

## 技術方針
- フレームワーク：Next.js（App Router・TypeScript）
- Vercel にデプロイ
- DB：Supabase（PostgreSQL）。テーブル構成は `docs/data_structure.md` 参照。
- 認証：Supabase Auth（Google OAuth）
- `prompt.ts`：EXAMPLESとbuildPromptを一元管理する共有モジュール。API routeから参照。
- `app/api/decompose/route.ts`：Next.js API route。プロンプト組み立てと Gemini API 呼び出しを担う。能力一覧・当人は？を一括で返す。
- `demo.html`：プロトタイプ用のデモ。仕様対象外。
- `data/samples.json`：実出力サンプルデータ。スキーマ：[{id, task, createdAt, abilities: [{title, description, person, solution}]}]。
- APIキーは環境変数（`GEMINI_API_KEY`）で管理。コードには書かない。
- モデル：Gemini 3.1 Flash Lite（`gemini-3.1-flash-lite`）
